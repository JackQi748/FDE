# 01 · RAG 检索增强生成（Retrieval-Augmented Generation）

## 一句话直觉

**先查证据，再让模型开口**——把「会说」变成「有据可查地说」。

---

## 直觉讲解

大语言模型的参数里压着训练期的世界知识，但对**企业私有文档、最新制度、工单细节**往往既不知道，也不该凭记忆编。RAG 的做法很朴素：

1. 把知识库切成可检索的片段并建索引  
2. 用户提问时，先检索出最相关的证据片段  
3. 把证据与问题一起塞进提示词，要求模型**只基于证据作答**（并引用）  
4. 证据不足时拒答或澄清，而不是「自信胡说」

```mermaid
flowchart LR
  Q[用户问题] --> A[鉴权 / 查询改写]
  A --> R[检索]
  R --> RR[重排可选]
  RR --> C[组装上下文]
  C --> G[生成 + 引用]
  G --> V[校验 / 护栏]
```

RAG **不是**「向量数据库产品名」，也不是「只要 embedding 就能上线」。它是一条端到端链路：语料治理 → 切块 → 嵌入/关键词索引 → 检索与过滤 → 组装 → 生成 → 评测与护栏。任何一环薄弱，都会表现为「答非所问、漏权限、引用对不上」。

和微调的分工可以记一句：

| 手段 | 擅长 | 不擅长 |
|------|------|--------|
| Prompt | 格式、角色、少量例子 | 灌入海量私有知识 |
| RAG | 动态、可审计的事实依据 | 改变模型「说话风格」本身 |
| 微调 | 稳定风格、领域用语、结构化输出 | 频繁变更的事实库（成本高） |

企业场景默认路径往往是：**RAG 扛事实，微调/提示扛风格与格式**。

## 工作示例

**场景**：客服助手回答「退货窗口是几天？」

| 步骤 | 动作 | 示例 |
|------|------|------|
| 语料 | 入库《售后政策 v3.2》 | `doc_id=POL-RET-032` |
| 切块 | 按条款切，带元数据 | `section=3.1, updated_at=2026-03-01, acl=public` |
| 检索 | 混合检索 top-20 → 重排 top-5 | 命中「自签收起 7 个自然日」条款 |
| 组装 | 系统提示：只能依据证据；列出引用编号 | 片段 `[1][2]` |
| 生成 | 「根据售后政策 v3.2 第 3.1 条，标准商品为 7 天……」 | 附可点击回源 |
| 失败 | 若检索为空或分数过低 | 「未在现行政策中找到明确条款，建议转人工」 |

**对比基线**（无 RAG）：模型可能答「14 天」——那是某电商常识幻觉，与你们公司政策无关。

**粗算成本感**：假设每次问答检索 5 段 × 400 token ≈ 2000 token 上下文，加上系统提示与问题，输入约 3k–6k token。相对「把整本手册塞进窗口」，既更省，也更可控。

## 面试常问取舍

**Q：为什么不直接把文档塞进超长上下文？**  
A：长上下文有上限、贵、且「大海捞针」效果不稳定；企业文档会持续增长与版本变更。RAG 用检索做**动态注意力预算**：只把当下相关的证据送进去。

**Q：RAG 还会幻觉吗？**  
A：会。常见来源：检索错了却被当成事实；多段证据冲突；模型忽略证据「自由发挥」。缓解：强制引用、证据不足拒答、重排、权限过滤、答案与引用一致性校验。

**Q：混合检索、重排、GraphRAG 要不要一上来全上？**  
A：先做最小闭环 + 评测集。召回不够再加混合/改写；排序不稳再加重排；多跳关系明显再考虑图谱。堆栈越深，运维与评测成本越高。

**Q：和 Agent 什么关系？**  
A：RAG 是「读知识」的一种能力；Agent 还可能多步规划、调工具写系统。很多产品是「工作流里嵌 RAG」，不必一上来全自主 Agent。

| 取舍维度 | 偏轻量 | 偏重量 |
|----------|--------|--------|
| 延迟 | 单路向量 top-k | 混合 + 重排 + 多查询 |
| 成本 | 小模型 + 短上下文 | 大模型 + 长证据包 |
| 正确性 | 引用 + 拒答 | 再加校验 Agent / 人工抽检 |
| 权限 | 元数据预过滤 | 行级 ACL + 审计日志 |

## FDE 现场怎么用

进场第一周，用客户语言把 RAG 画成「查手册再回答」，并同步四件资产：

1. **语料与版本**：谁维护、更新频率、废止如何下线  
2. **切片与索引**：块大小、重叠、embedding 模型与版本号  
3. **元数据**：权限标签、产品线、时间、来源 URL  
4. **评测集**：至少 50–100 条真实问题 + 期望引用/答案要点  

POC 验收不要只看「感觉答得对」，要看：

- 带引用的正确率 / 拒答率  
- 权限用例（不该看见的文档绝不能出现）  
- P95 延迟与单次 token 成本  
- 索引新鲜度（政策更新后多久可被搜到）

常见翻车：权限只写在 prompt 里；切块切断表格导致条款残缺；没有「证据不足」策略导致胡编。

## 指标与验收口径

上线前至少固定这组数字，避免「感觉还行」：

| 指标 | 含义 | 起步目标感 |
|------|------|------------|
| 带引用正确率 | 答案对且引用可回源 | 按业务定，需基线 |
| 拒答准确率 | 该拒则拒、不该拒不胡拒 | 与误杀一起看 |
| 权限对穿数 | 禁止文档进入上下文次数 | **必须为 0** |
| P95 端到端延迟 | 含检索+生成 | 写进 SLA |
| 单次成本 | 输入输出 token 费用 | 写进容量规划 |

评测集要「像真实用户」：口语、缺主语、带编号、带权限边界。工程师捏的标准问法会高估效果。

## 演进路线（避免一口吃成胖子）

1. **M0**：单路检索 + 强制引用 + 拒答 + 权限预过滤  
2. **M1**：混合检索 + 基础改写  
3. **M2**：重排 + 新鲜度 SLA  
4. **M3**：按坏案例决定 Contextual / 图谱 / 晚交互  

每一跳都要用同一套评测集回归，防止「加了组件反而掉点」。
