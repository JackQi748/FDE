# 05 · 重排与两阶段检索（Rerank）

## 一句话直觉

**先广撒网，再精挑细选**——便宜快速的召回负责「有没有」，贵一点的重排负责「谁排前面」。

---

## 直觉讲解

信息检索长期使用两阶段架构，RAG 只是把它接到了 LLM 前面：

1. **第一阶段·召回（Retrieval）**：用 ANN、BM25 或混合检索，从十万～亿级库中取 top-N（常见 50–100）  
2. **第二阶段·重排（Rerank）**：用交互更强的模型对这 N 条打分排序，只把 top-k（常见 3–8）送进提示词  

关键约束：**重排无法复活未召回的文档**。若真相关在全库里根本没进 N，交叉编码器再强也没用。因此「召回不够」要回到混合检索、切块、改写；「相关在第 30 名」才优先加重排。

```mermaid
flowchart LR
  Corpus[语料库] --> S1[召回 top-N]
  S1 --> S2[重排 top-k]
  S2 --> Asm[组装上下文]
  Asm --> Gen[生成]
```

| 重排手段 | 机制 | 延迟/成本 | 适用 |
|----------|------|-----------|------|
| 交叉编码器 | 查询与文档拼接交互编码 | 中 | 默认首选 |
| 专用 rerank API | 托管交叉编码器 | 中，按条计费 | 要快上线 |
| LLM 当裁判 | 提示模型打分/选 top | 高 | 复杂相关定义 |
| 业务规则融合 | 新鲜度、渠道、点击 | 低 | 强业务先验 |

生产必须设计**超时降级**：重排 100ms 预算用尽则返回融合分排序，并打点 `rerank_skipped`。整链因重排 504 比「稍微排得差一点」更伤客户信任。

## 工作示例

**场景**：银行制度问答。混合检索 N=80，人工标注显示真相关常落在 12–45 名。

| 指标 | 无重排 top-5 | 交叉编码器重排 top-5 | 说明 |
|------|--------------|----------------------|------|
| Hit@5 | 0.61 | 0.84 | 顺位被纠正 |
| 业务答案正确率 | 0.66 | 0.82 | 上下文更干净 |
| P95 增加 | — | +90~150ms | N=80 时 |
| 空结果率 | 同左 | 同左 | 重排不改变空召回 |

**LLM 重排示例提示（示意）**：给定问题与 20 条候选，要求只输出 JSON 排序 id 列表，禁止改写正文。N 应≤20，否则成本与延迟失控。

**负面案例**：把 N 提到 500「为了更准」，重排 P95 到 1.2s，用户以为系统挂了。正确做法是提高第一阶段质量，而不是无限增大 N。

**与多样性**：多查询改写会产生近重复块；重排前后都要按 `doc_id`+指纹去重，避免 top-5 其实是同一段的五种切法。

## 面试常问取舍

**Q：什么时候可以不上重排？**  
A：当 top-k 业务指标已达标且延迟紧张时。重排是优化项，不是宗教仪式。

**Q：交叉编码器 vs LLM 裁判？**  
A：多数企业文档问答，小/中型 reranker 足够。LLM 裁判适合「相关性定义很业务化」（如必须同辖区、同产品世代）且 N 很小的情况。

**Q：重排要不要看权限？**  
A：权限应在召回前过滤。重排阶段不应再看见无权限文档；也不要幻想用重排「排掉」敏感档。

**Q：如何证明重排值不值？**  
A：离线对比 nDCG/MRR/业务正确率 + 在线 A/B 的 P95 与用户二次追问率。

| 取舍 | 轻量 | 重量 |
|------|------|------|
| N | 20–40 | 100+ |
| 模型 | 小型 reranker | LLM 裁判 |
| 降级 | 必须 | 必须 |
| 去重 | 简单 doc_id | 指纹+标题归一 |

## FDE 现场怎么用

架构评审时把「召回服务 / 重排服务 / 生成服务」画成三个框，标清 SLA：例如召回 80ms、重排 120ms、生成流式 TTFT 1.5s。明确降级开关由配置中心控制，而不是改代码。

对业务方话术：多花约 0.1 秒，是为了少把「看起来像、其实不是」的段落送进模型，从而减少一本正经的错误引用。

验收包建议包含：

- 有无重排的离线对比表  
- 超时降级演练记录  
- 重排前后 top-k 样例各 20 条（给人看）

## 重排服务的工程化

- **批处理**：一条查询对 N 条候选批量打分，降低 HTTP 开销  
- **缓存**：高频查询的重排结果短 TTL 缓存（注意权限键）  
- **模型热备**：主 reranker 失败切融合分，而不是 500  
- **特征融合**：可把「新鲜度」「业务权重」加进最终分，不全信模型
