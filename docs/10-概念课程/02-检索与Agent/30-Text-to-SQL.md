# 30 · Text-to-SQL

## 一句话直觉

**用自然语言问数，但数据库仍只看见受控的 SQL**——模型负责起草，网关负责安全执行。

---

## 直觉讲解

Text-to-SQL 把用户问题编译成 SQL。价值大、风险也大：一次幻觉 join 就能扫爆表或泄密。企业级做法是「编译器+沙箱」，不是「模型直连生产库」。

安全控制清单：

| 控制 | 做法 |
|------|------|
| 账号 | 只读、行级权限、限库限表 |
| 表白名单 | 仅暴露语义层允许的表/视图 |
| 语义层 | 指标口径预定义，减少随意 SQL |
| 静态分析 | 禁 DROP/UPDATE/导出大表、限 join 深度 |
| 执行 | 超时、行数上限、队列 |
| 审计 | 问句、SQL、用户、耗时全记 |
| 确认 | 高代价查询 HITL |

```mermaid
flowchart LR
  Q[自然语言] --> Schema[相关schema检索]
  Schema --> Gen[生成SQL]
  Gen --> Check[校验/改写]
  Check --> Run[只读执行]
  Run --> NL[结果解释]
```

准确率依赖：库表注释质量、示例问答、指标定义、是否允许多步澄清。

## 工作示例

**问**：「上月华东区已支付订单的 GMV？」  
**好 SQL**：带日期边界、区域码、支付状态枚举，走汇总视图。  
**坏 SQL**：扫明细百万行、用错时区、把「已下单」当「已支付」。

**流程增强**：

1. 先检索「指标字典」得官方口径  
2. 生成 SQL  
3. EXPLAIN / 静态检查  
4. 执行抽样  
5. 模型用表格总结，并展示 SQL 给分析师展开  

**评测**：执行正确率、口径一致率、危险 SQL 拦截率、P95 耗时。

## 面试常问取舍

**Q：能不能给模型看全库 schema？**  
A：大库不行。应检索相关表结构，防窗口爆炸与乱 join。

**Q：和 BI 机器人区别？**  
A：有语义层/指标服务时更稳；纯 Text-to-SQL 适合探索，不适合无治理的财务正式数。

**Q：写操作？**  
A：默认禁止。任何写 SQL 走工单系统。

| 取舍 | 自由 SQL | 语义层+模板 |
|------|----------|-------------|
| 灵活 | 高 | 中 |
| 可信 | 低 | 高 |
| 企业默认 | 否 | 是 |

## FDE 现场怎么用

先交付「指标问答」而不是「任意 SQL」。与数仓团队共建语义层。POC 用只读副本。把「展示 SQL」作为信任设计，而不是藏起来。

## 语义层例子

指标 `paid_gmv` = 已支付订单金额求和，时区 `Asia/Shanghai`，剔除测试渠道。  
用户说「GMV」必须映射到该指标，而不是模型即兴 sum 某列。

## 澄清对话

缺时间范围就问；不要默认「最近」。澄清轮次计入体验，却比错数便宜。

## 对照速记

本篇核心可以压成三句话，便于面试或客户沟通临场调用：

1. **问题本质**：本主题要解决的失败是什么。  
2. **默认做法**：企业场景下通常先怎么做。  
3. **升级信号**：什么指标/坏案例出现才加重方案。  

结合上文表格与示例，把这三句话改写成你客户行业的语言；若写不出来，说明概念尚未内化，应回到「工作示例」一节重做一遍角色扮演。
