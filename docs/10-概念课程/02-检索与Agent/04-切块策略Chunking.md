# 04 · 切块策略（Chunking）

## 一句话直觉

**检索的原子是「块」不是「文件」**——切错边界，等于给模型一堆残缺证据还要求它判案。

---

## 直觉讲解

切块（chunking）决定三件关键事：**检索粒度**、**证据完整性**、**索引与窗口成本**。用户问的是业务问题，系统匹配的却是块；生成时引用的也是块。因此「PDF 有 200 页」并不重要，重要的是这 200 页变成怎样的可检索原子。

常见策略对比：

| 策略 | 适用语料 | 优点 | 风险 |
|------|----------|------|------|
| 固定长度 + 重叠 | 快速起步、结构弱 | 实现简单 | 切断表格、条款、代码 |
| 按标题/段落结构 | 手册、制度、Wiki | 边界自然 | 依赖解析质量 |
| 按语义边界 | 结构混乱的长文 | 主题更凝聚 | 调参与实现复杂 |
| 按业务对象 | 合同条款、工单、FAQ、API | 往往效果最好 | 要懂领域结构 |
| 父子 / 多粒度 | 需精定位又要宽上下文 | 召回细、生成看父块 | 链路更复杂 |

每块建议绑定元数据：`doc_id, section_path, page, acl_tags, updated_at, version, source_uri`。权限、新鲜度、引用回源都挂在块上，而不是「整文件一个向量」。

```mermaid
flowchart LR
  Doc[原始文档] --> Parse[解析与清洗]
  Parse --> Chunk[切块]
  Chunk --> Meta[写入元数据]
  Meta --> Index[嵌入 / 关键词索引]
  Index --> Eval[用评测集回归]
```

重叠（overlap）用于降低「答案落在切割缝」的漏召回，但会增加存储与重复命中。表格、有序列表、代码块应尽量**整块保留**，或先转成「一行一条可读文本」再切。扫描件与复杂版面要先过文档解析（见第 31 篇），否则切块只是在放大 OCR 错误。

切块策略本身要**版本化**：`chunk_strategy=struct-v3`。改策略 = 换索引，必须重建并在评测集上回归，不能偷偷在生产改刀法。

## 工作示例

**场景 A：员工手册 PDF（结构清晰）**  
按「编 / 章 / 条」切；目标块长约 200–600 汉字；`section_path=考勤管理/第12条`；条款标题写入块首，避免块内缺主语。

**场景 B：价目表与费率表**  
禁止固定 token 横切。一表一块或「一行一费率」对象化；附加列名到文本：`渠道=线上; 费率=0.6%`。否则检索命中半行数字，模型会读出错误费率。

**场景 C：客服工单**  
按工单 ID 聚合；块内保留「现象 / 原因 / 处理 / 结果」字段。纯按 500 字切会把处理结果拆到下一块，导致「只检索到现象」。

**场景 D：API 参考**  
以 endpoint 为原子：路径、方法、参数、示例、错误码同块。错误码表可二级切，但要带父 endpoint 元数据。

**对比实验（写进 POC）**：

| 方案 | recall@5 | 引用可点回率 | 索引块数 |
|------|----------|--------------|----------|
| 固定 512+50 重叠 | 0.71 | 0.62 | 1.0× |
| 按标题结构 | 0.83 | 0.88 | 0.9× |
| 条款对象化 | 0.89 | 0.93 | 1.1× |

数字是示意：重点是**用客户语料跑这张表**，而不是背网上经验值。

## 面试常问取舍

**Q：块到底多大合适？**  
A：没有万能数。中文制度类常从 256–512 汉字等价长度试起，但优先保证语义完整。过大导致噪声进窗口，过小导致缺上下文与主语。

**Q：要不要上语义切块 / late chunking？**  
A：基线（结构切 + 元数据）跑稳并完成评测前，不建议一上来上复杂方案。坏案例证明「边界问题」再升级。

**Q：一块多向量还是一向量？**  
A：默认一块一向量。多表示（标题向量+正文向量）是优化项，需额外存储与融合逻辑。

**Q：改切块要停服吗？**  
A：最佳是蓝绿索引：新策略建新 collection，评测过再切流量；保留旧索引回滚窗口。

| 取舍 | 小块 | 大块 |
|------|------|------|
| 定位精度 | 高 | 低 |
| 证据完整 | 易缺上下文 | 更完整 |
| 窗口效率 | 可拼多块 | 单块占预算 |
| 索引体积 | 块数多 | 块数少 |

## FDE 现场怎么用

现场工作坊选客户真实的三类文档：①结构良好制度 ②表格密集 ③工单/邮件。现场展示「固定切切断表格」与「对象化切」的检索差异，让业务自己投票。

写入项目范围的交付物：

- 切块策略说明（含表格/图片/页眉页脚规则）  
- `chunk_strategy` 版本与重建 runbook  
- 与解析管道的接口契约（解析失败不得静默切垃圾文本）  
- 评测集中标注「期望引用落在哪一节」  

常见扯皮点：研发认为「已经按 500 字切了就是 RAG」，业务认为「条款答错就是模型不行」。FDE 要能指出根因在切块边界。

## 切块与引用体验

用户点击引用时期望落到「正确章节」而不是 PDF 第 1 页。因此块元数据要能映射回：

- 页码 / 锚点 / 标题路径  
- 源 URI 与版本  
- 高亮用的字符偏移（若有）  

前端展示「第 3.2 节 · 退货窗口」比只显示 `chunk_9182` 更能建立信任。

## 多粒度策略简图

| 层 | 粒度 | 用途 |
|----|------|------|
| 子块 | 句子/小段 | 精检索 |
| 父块 | 节/条款 | 送入 LLM 的上下文 |
| 文档摘要 | 篇级 | 路由与过滤 |

先实现单粒度，评测不够再上父子。避免第一周就建三层索引却无人维护。
