# Ontology（语义层/企业本体）

## 直觉

Ontology 把企业里的对象、属性、链接与动作变成**可计算语义**：不只是表，而是「工单—资产—人员—权限」的意义网络。AI 落在语义层上，比落在散表 SQL 上更可治理。

## 讲解

### 为何 FDE 在意

- 统一指标与实体，减少各说各话
- 权限可挂在对象边
- Agent 工具对准「动作」而非裸 API
- 变更有类型，可审计

与数仓「语义层/指标层」相通，但更强调对象与操作。平台产品（如 Foundry Ontology）是一种工业化实现，概念本身不绑定单一厂商。

## 工作示例

客户有 12 套「客户」定义。先建最小 Ontology：Customer、Contract、Ticket 与三两关键链。助手只通过对象 API 读，准确与权限投诉下降。

## 面试取舍

取舍：先建模 vs 先 demo。面试说「薄切片对象模型」而非企业一年建模。

## FDE用法

1. Discover 勾画出核心对象 10 个以内。
2. 不追求完美全集。

## 易混点

围绕「Ontology（语义层/企业本体）」，现场最常见混淆：

1. **把 Demo 稳定性当成生产稳定性**：单次成功路径不等于可值班、可回滚、可审计。
2. **只优化平均值**：P50 很好时 P99 与错误预算可能已经烧穿。
3. **安全控制后置**：权限、驻留、密钥与网络不是上线前贴纸。
4. **成本与质量拆成两张嘴**：没有单位经济的「更好」不可持续。
5. **缺少明确 owner**：指标无人看，事故无人关。

## 运行手册摘要

落地「Ontology（语义层/企业本体）」时，建议最小 Runbook 条目：

| 项 | 内容 |
|----|------|
| 触发条件 | 何时启用/告警/降级 |
| 首要动作 | 前 5 分钟做什么 |
| 证据 | 看哪些仪表盘与 trace |
| 回滚 | 精确到版本/旗标/路由 |
| 沟通 | 客户侧通知模板 |
| 复盘 | 24h 内写清根因与门禁缺口 |

## 反模式

- 无门禁从 POC 直接全员开放。
- 重试无抖动、无限次，制造重试风暴。
- 限流只限别人，自己批处理打爆依赖。
- 可观测只有日志文件，无线索关联。
- SLO 写成「尽量快尽量准」而不可计算。

## 一周落地节奏（示例）

| 日 | 动作 |
|----|------|
| D1 | 画请求路径与依赖；标出爆炸半径 |
| D2 | 定 SLI/成本/安全基线与告警 |
| D3 | 实现最小硬化（超时/重试/幂等/限流之一组） |
| D4 | 影子或金丝雀验证 |
| D5 | 写 Runbook 与客户沟通材料 |

## 面试 60 秒版本

谈到「Ontology（语义层/企业本体）」，我会先画链路与爆炸半径，再谈控制手段与可观测证据，最后给回滚与单位经济。FDE 的分数来自可运营，而不是只能演示。

## 速查清单

- 成功与失败是否可测、可告警？
- 是否有超时、重试、幂等、限流的明确策略？
- 是否具备 trace/metrics/log 三件套与版本标签？
- 是否定义降级与供应商故障转移？
- 是否写清部署模型与数据驻留？
- 是否有错误预算与发布冻结规则？
- 是否能在 5 分钟内定位「哪一跳」坏了？
- 客户 owner 与升级路径是否点名？
