# 灾难性遗忘

## 直觉

神经网络在学新任务时，旧任务性能急剧下降，称为**灾难性遗忘**。持续微调、只喂新业务语料、或频繁改适配器，都可能让「去年还能答的制度题」突然不会。

## 讲解

### 缓解思路

| 方法 | 直觉 |
|------|------|
| 回放（replay） | 混旧样本再训 |
| 正则约束（EWC 等） | 锁重要权重 |
| 多任务/联合训 | 同时见各域 |
| 适配器隔离 | 新域新 LoRA，路由选择 |
| 冻结骨干 | 只训头/检索侧 |

RAG 架构常比「把知识灌进权重」更抗遗忘：知识在索引，模型侧重推理与遵从。

## 工作示例

新政策上线，微调后新问 85%，旧政策问答从 90%→60%。处置：回放旧金标 30%；或新政策 LoRA 分路由；回归集含旧政策硬集。

## 面试取舍

取舍：联合训稳但重；多适配器灵活但增编排复杂度。面试联系持续学习与门禁。

## FDE用法

1. 任何续训必跑「旧能力金标」。
2. 优先考虑索引更新 vs 权重更新。
3. 版本化权重与一键回滚。

## 易混点

围绕「灾难性遗忘」，现场最常见的概念混淆：

1. **把代理指标当成业务结果**：技术分上涨不等于采纳、周期或风险下降。
2. **只看平均、不看切片**：整体健康时，高风险长尾可能已经崩盘。
3. **同时改多个旋钮**：无法归因，复盘只能靠叙事。
4. **忽略标注/量规版本**：指标不可比，却被讲成「模型变强」。
5. **缺乏回滚故事**：说得清正向收益，说不清如何止损。

## 指标与日志建议

若要把「灾难性遗忘」落到可运营状态，最少保留：

| 字段/信号 | 用途 |
|-----------|------|
| request_id / trace_id | 对齐离线、影子与在线 |
| 策略/模型/提示版本 | 归因与回滚 |
| 自动分 + 人工抽检标记 | 校准与审计 |
| 延迟分位与成本 | 防止质量优化打爆预算 |
| 错误类标签 | 驱动错误本与金标回灌 |

日志要能回答：哪次改动、对哪类用户、在哪一环坏了。

## 反模式

- 用公开 Benchmark 替代客户域金标，还把名次写进验收。
- 在持出集上反复调参，再宣称泛化良好。
- 只有开心路径 demo，没有拒答、权限、工具失败注入。
- 汇报时隐藏置信区间与样本量。
- 让业务方「凭感觉」改通过线，而不改量规文本。

## 一周落地节奏（示例）

| 日 | 动作 |
|----|------|
| D1 | 写清问题、代价、成功定义；找到数据主人 |
| D2 | 搭最小可重复脚本与基线分 |
| D3 | 分层抽样补强；标注重争议题 |
| D4 | 做一次单变量改进并对比 |
| D5 | 复盘失败类；更新错误本与门禁 |

若五天内无法复现基线，优先修数据与工程，而不是换更大模型。

## 面试 60 秒版本

「灾难性遗忘」我抓三件事：定义要可测、证据要可重复、上线要可控。我会先对齐业务代价，再选指标与门禁，用离线回归兜已知题，用金丝雀/影子控制爆炸半径，并把版本、成本、回滚写进同一张表。

## 速查清单

- 能否用业务语言解释本主题解决什么问题？
- 是否写清成功指标、失败定义与不可接受副作用？
- 是否区分离线可复现信号与线上真实行为？
- 是否准备至少一个反例说明何时不适用？
- 是否把成本、延迟、风险与可运维性写入权衡表？
- 是否约定回归节奏与明确 owner？
- 是否避免只报单一总分，保留切片与错误本？
- 是否对标注/裁判做过抽检校准？
- 是否记录决策以便复盘？
- 是否准备回滚或降级路径？
