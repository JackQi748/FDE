# 评测 RAG 系统

## 直觉

RAG 坏可能坏在检索、坏在生成、坏在编排。端到端一个「答案分」会掩盖病因。应分层：**检索质量 → 生成忠实/相关 → 端到端业务指标**。

## 讲解

### 分层指标

| 层 | 指标例 | 问什么 |
|----|--------|--------|
| 检索 | Recall@k、nDCG、命中金标 chunk | 证据在不在 |
| 生成 | 忠实度、幻觉率、引用正确率 | 有没有瞎编 |
| 相关 | 答案相关性、意图满足 | 有没有答非所问 |
| 系统 | 延迟、成本、拒答率、采纳率 | 能否上线 |

金标可标「必须命中的文档/段」；答案可开放，用裁判+人工。

### 常见失效

- 检索对但生成忽略证据
- 检索错但模型靠参知答对（不可复现、有合规风险）
- 切块策略杀召回
- 权限过滤后检索集空洞未处理

## 工作示例

一周评测搭建：

1. 80 问，标 gold_chunk_ids
2. 报 Recall@5、MRR
3. 对生成跑忠实度/相关性裁判
4. 切片：多跳、表格、稀有产品

诊断矩阵：

| 检索 | 答案 | 动作 |
|------|------|------|
| 差 | 差 | 先改检索/切块 |
| 好 | 差 | 改提示/引用约束 |
| 差 | 好 | 查是否靠参知；补拒答 |
| 好 | 好 | 看延迟成本 |

## 面试取舍

取舍：只优化检索榜可能伤害生成体验；只看答案分会放过权限与引用问题。面试应主动画分层。

## FDE用法

1. 发版门禁：检索烟测 + 端到端持出 + 安全拒答集。
2. 与客户演示用「坏例复盘」而非只秀好例。
3. 索引变更当模型变更：重跑检索回归。

## 速查清单

交付或面试前快速自检：

- 能否用业务语言解释「评测 RAG 系统」解决什么问题？
- 是否写清成功指标、失败定义与不可接受副作用？
- 是否区分离线可复现信号与线上真实行为？
- 是否准备至少一个反例说明何时不适用？
- 是否把成本、延迟、风险与可运维性写入权衡表？

> 原创概念笔记：评测 RAG 系统。

## 易混点

围绕「评测 RAG 系统」，现场最常见的概念混淆：

1. **把代理指标当成业务结果**：技术分上涨不等于采纳、周期或风险下降。
2. **只看平均、不看切片**：整体健康时，高风险长尾可能已经崩盘。
3. **同时改多个旋钮**：无法归因，复盘只能靠叙事。
4. **忽略标注/量规版本**：指标不可比，却被讲成「模型变强」。
5. **缺乏回滚故事**：说得清正向收益，说不清如何止损。

## 指标与日志建议

若要把「评测 RAG 系统」落到可运营状态，最少保留：

| 字段/信号 | 用途 |
|-----------|------|
| request_id / trace_id | 对齐离线、影子与在线 |
| 策略/模型/提示版本 | 归因与回滚 |
| 自动分 + 人工抽检标记 | 校准与审计 |
| 延迟分位与成本 | 防止质量优化打爆预算 |
| 错误类标签 | 驱动错误本与金标回灌 |

日志要能回答：哪次改动、对哪类用户、在哪一环坏了。

## 反模式

- 用公开 Benchmark 替代客户域金标，还把名次写进验收。
- 在持出集上反复调参，再宣称泛化良好。
- 只有开心路径 demo，没有拒答、权限、工具失败注入。
- 汇报时隐藏置信区间与样本量。
- 让业务方「凭感觉」改通过线，而不改量规文本。

## 一周落地节奏（示例）

| 日 | 动作 |
|----|------|
| D1 | 写清问题、代价、成功定义；找到数据主人 |
| D2 | 搭最小可重复脚本与基线分 |
| D3 | 分层抽样补强；标注重争议题 |
| D4 | 做一次单变量改进并对比 |
| D5 | 复盘失败类；更新错误本与门禁 |

若五天内无法复现基线，优先修数据与工程，而不是换更大模型。
