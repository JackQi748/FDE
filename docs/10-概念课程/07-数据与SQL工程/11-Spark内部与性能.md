# Spark 内部与性能

一句话直觉：Spark 把大数据切成分区并行算；慢与 OOM 多半来自 shuffle、倾斜、小文件与「把集群当单机 pandas」。

## 直觉讲解

**Apache Spark** 是分布式计算引擎：Driver 规划作业，Executor 执行任务。对 FDE，重点是性能直觉而非背源码。

关键概念：

| 概念 | 直觉 |
|------|------|
| Partition | 并行度的基本块；太少浪费，太多调度开销 |
| Stage / Task | 宽依赖（shuffle）切分 stage |
| Shuffle | 跨节点按键重分区；贵且易炸 |
| Catalyst / Tungsten | SQL/DataFrame 优化与执行 |
| AQE | 运行时合并分区、处理倾斜等 |

```mermaid
flowchart LR
  D[Driver] --> S1[Stage 扫描]
  S1 -->|shuffle| S2[Stage 聚合]
  S2 --> O[写出]
```

常见爆炸半径：

1. **数据倾斜**：某 key 占 80% 流量，单 task 撑爆  
2. **宽依赖过多**：反复 shuffle  
3. **收集到 Driver**：`collect()` 大结果  
4. **小文件**：读百万小对象，元数据先累死  
5. **倾斜 join**：大表与热键  

DataFrame/SQL 通常优于手写 RDD：能吃优化器。PySpark 里避免逐行 Python UDF 热路径；必要时用向量化/Spark 内置函数。

## 工作示例（数字/场景）

**场景 A：日志聚合 OOM**

作业对 `user_id` groupBy 计数。发现某爬虫 id 占 30% 行。手段：过滤机器人、盐化热键、两阶段聚合。

**场景 B：AI 特征批处理超时**

全量 join 用户维与 90 天事件。优化：

1. 只读需要列  
2. 事件先按日分区裁剪  
3. 广播小维表（确认内存）  
4. 结果写分区表，避免单目录海量小文件  

**场景 C：笔记本 vs 集群**

客户样例 10 万行在笔记本秒级；生产 10 亿行。FDE 要拒绝「笔记本跑通=生产方案」，改为抽样计划 + 仓内/集群容量评估。

| 症状 | 先看 | 动作 |
|------|------|------|
| 单 task 极慢 | 倾斜 | salt / 过滤热键 |
| shuffle 读巨大 | 宽依赖 | 预聚合、减膨胀 |
| Driver OOM | collect/广播过大 | 改写、增限 |
| 启动久 | 小文件/列表 | 合并文件 |

**数字感**：同逻辑从 200 分区提到 2000，不一定更快——调度与文件数可能变差。用测量说话。

## 面试常问取舍

1. **Spark vs 仓内 SQL**  
   - 重 Python/ML、复杂图、多源非结构化 → Spark/同类。  
   - 规整 SQL 转换 → 仓内往往更省心。

2. **RDD vs DataFrame**  
   - 新代码默认 DataFrame/SQL；RDD 留给特殊控制。

3. **精确去重 vs 近似**  
   - `countDistinct` 贵；HyperLogLog 等近似看场景。  
   - 与 [13-去重与LSH](./13-去重与LSH.md) 联动。

4. **动态分区覆盖踩坑**  
   - 写错分区模式可能清空意外分区——权限与单元测试要有。

## FDE 现场怎么用

1. 会读 Spark UI：stage 时间、shuffle 大小、倾斜 task。  
2. 与平台组对齐默认资源、AQE、文件格式（Parquet/Delta）。  
3. AI 管道：embedding 批处理注意对外 API 限流，别把 Executor 打成 DDoS。  
4. 成本：失败重试的集群小时费写进估算。  
5. 口条：「先减 shuffle 与扫描，再加 executor。」

## 深入：UI 阅读与文件格式

### Spark UI 最小路径
Jobs → 最慢 Stage → Tasks 时长直方图（看倾斜）→ Shuffle Read/Write → 看是否 spill。

### 存储格式
列式 Parquet/ORC + 压缩；避免文本巨型 CSV 当生产主存。Delta/Iceberg 上注意提交频率与小文件。

### UDF 税
Python UDF 打断优化并增加序列化。优先内置函数；必须 UDF 时测吞吐，考虑向量化/Scala。

### 与仓协同
能下推到仓的转换就下推；Spark 留给仓不擅长的重加工与多源整合。

### 课堂小结
性能工作是测量驱动的减法：减数据、减 shuffle、减倾斜，最后才加机器。

## 速查清单与一周落地

### 进场 60 秒自检
-  成功 标准是否可测、可告警？
- 失败时能否阻断下游或降级，而不是静默？
- 关键对象是否有明确 owner 与版本？
- 是否存在可演示的回滚/重跑路径？
- 安全与隐私控制是否与功能同迭代，而非上线贴纸？

### 建议一周节奏
| 日 | 动作 |
|----|------|
| D1 | 画现状与爆炸半径；点名权威源/身份/边界 |
| D2 | 定最小验收数字与反例（应失败用例） |
| D3 | 落地最小控制或管道切片 |
| D4 | 用真实量级/红队样本验证 |

### 面试 60 秒版本
先讲问题的业务爆炸半径，再讲 2–3 个关键控制与可观测证据，最后给回滚/门禁。FDE 分数来自可运营，而不是名词堆叠。

### 常见反模式（再强调）
- 只有快乐路径 Demo，没有否定测试  
- 重试/自动化放大事故（缺幂等或缺开关）  
- 把提示词/文档当唯一强制执行点  
- 指标不可计算或无人看  
- 成本、质量、安全拆成三张互相矛盾的嘴
