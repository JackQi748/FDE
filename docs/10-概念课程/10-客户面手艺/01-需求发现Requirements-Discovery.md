# 01 · 需求发现 Requirements Discovery

一句话直觉：客户开口常是方案（「要个聊天机器人」），需求发现的任务是挖到**可验证的用户结果与约束**，再决定要不要 AI。

## 直觉讲解

**需求发现**不是开会记愿望清单，而是用访谈与现场观察，把模糊诉求收敛成：

1. 谁在什么场景要什么结果  
2. 今天怎么做、失败代价是什么  
3. 数据/权限/合规硬约束  
4. 怎样算「更好」的可测指标  

FDE 的发现与面试 [Decomposition](../../04-面试通关/Decomposition拆解面.md) 同构：先问题部件，后模型与架构。

```mermaid
flowchart LR
  Ask[表面方案请求] --> Why[连续追问为何]
  Why --> Flow[跟一次真实作业]
  Flow --> Metric[成功度量]
  Metric --> Constraint[数据与风险约束]
  Constraint --> Problem[问题陈述]
  Problem --> Next[可证伪的下一步]
```

危险信号：「先做个 Demo 再说需求」——可以，但必须标注假设，否则 Demo 会变成范围监狱。

## 工作示例（数字/场景）

**场景 A：「我们要客服 GPT」**

表面：聊天机器人。跟岗两小时发现：

- 真正耗时是「查三套系统拼订单时间线」  
- 坐席怕的是错退款，不是话术不够炫  
- 成功指标是 AHT（平均处理时长）与二次进线率，不是点赞  

问题重写：在权限内检索订单事件并生成**可引用**摘要，退款动作保持人工确认。AI 形态从「闲聊」变成「工具型助手」。

**场景 B：发现访谈六问（压缩）**

| 问 | 挖什么 |
|----|--------|
| 今天谁一步步怎么做？ | 真实工作流 |
| 怎样算做好？谁看什么数？ | 指标 |
| 最近一次失败代价？ | 风险 |
| 数据在哪、能否出网？ | 约束 |
| 为什么是现在？ | 动机/政治 |
| 只能改善 20% 选哪？ | 优先级 |

完整提纲见交付方法论中的需求发现文与工具箱访谈清单。

**场景 C：政治性需求**

业务要自动化，安全要禁一切外发。发现阶段就要把两方拉到同一张「约束表」，避免你做成夹心饼干。

## 面试常问取舍

1. **多问 vs 显得不懂**  
   - 好业务细节是专业；装懂直接开干是风险。  
   - 用「带我走一笔真实单」代替抽象讨论。

2. **先方案 vs 先问题**  
   - 面试 Decomposition：先拆问题。  
   - 客户急要 Demo：给 Walking Skeleton，但书面锁假设。

3. **指标谈不拢怎么办**  
   - 先定代理指标（升级率、编辑率）与人工抽检，再谈完美业务 KPI。

4. **需求会变**  
   - 发现产出的是「当前最硬约束 + 可证伪假设」，不是永恒 PRD。

## FDE 现场怎么用

- **第一周交付物**：问题陈述一页纸 + 约束表 + 样例数据清单 + 下一周可证伪实验。  
- **禁止**：在未跟岗前承诺「准确率 95%」。  
- **与销售/解决方案对齐**：把「聊天机器人」翻译成结果语言，避免合同写死错误形态。  
- **记录**：假设登记册（Assumption Log）——每条假设有验证日期。

## 深入：问题陈述模板

```text
【用户】在【场景】下需要【结果】；
今天靠【现状】完成，主要痛点是【痛点】；
成功时【指标】改善【幅度假设】；
硬约束：【数据驻留/权限/延迟/预算】；
明确不做：【非目标】。
```

### 发现工作坊 90 分钟议程（示例）

| 分钟 | 内容 |
|------|------|
| 0–15 | 目标与非目标 |
| 15–40 | 跟故事：最近一笔真实案例 |
| 40–60 | 指标与失败代价 |
| 60–80 | 约束与系统地图 |
| 80–90 | 假设列表与下周实验 |

### 反模式

- 把干系人职位当需求（「CTO 想要 Agent」）。  
- 只访谈支持 AI 的冠军用户。  
- 收集了 30 个愿望却没有排序原则。

## 课堂小结

需求发现把你从「模型安装工」变成「结果负责人」。下一篇把发现结果锁成范围，防止试点吞掉整个企业改造。
