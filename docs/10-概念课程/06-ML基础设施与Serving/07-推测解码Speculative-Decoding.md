# 推测解码 Speculative Decoding

一句话直觉：让小而快的「草稿模型」先猜后面一串 token，大模型一次核对——对了就白嫖多步，错了就从分歧点重来，常能加速而不改大模型输出分布（在理想验证下）。

## 直觉讲解

自回归逐步解码受限于大模型每步延迟。**推测解码（speculative decoding）** 基本套路：

1. **起草（draft）**：小模型（或启发式）快速生成 γ 个候选 token；  
2. **验证（verify）**：大模型并行对这 γ 个位置打分/接受拒绝；  
3. **接受前缀**：按算法接受一致前缀，拒绝后从该点由大模型采样继续。

正确实现下，最终分布可与「只跑大模型」一致（无损加速）；若用近似接受规则，可能有损换速度。

```mermaid
flowchart LR
  D[Draft 小模型] -->|γ tokens| V[Target 大模型验证]
  V -->|接受 k≤γ| O[输出]
  V -->|拒绝| D
```

变体：同一模型的多层草稿、检索启发草稿、Medusa 多头等——现场记：**草稿质量 × 验证成本** 决定净加速。

## 工作示例（数字/场景）

**场景 A：何时划算**

| 条件 | 预期 |
|------|------|
| 草稿接受率高（模板化、代码补全） | 加速明显 |
| 高随机、开放闲聊、温度高 | 接受率低，可能无加速甚至更慢 |
| 草稿太大 | 起草本身太慢，吃掉红利 |
| batch 很大 | 验证并行收益与调度更复杂 |

经验：先在**你的流量样本**上测 tokens/s 与 P95，不要引用公网博客倍数。

**场景 B：企业助手**

系统提示固定、回答偏结构化 → 接受率尚可。打开后：TTFT 变化不大（仍要 prefill），解码阶段 tokens/s ↑；成本看是否多占一张小模型卡。

**场景 C：与门禁**

无损模式：金标应接近一致；若框架近似，必须跑回归。记录 `speculative=on/off` 版本。

## 面试常问取舍

1. **推测解码 vs 直接换小模型**  
   - 要大模型质量 → 推测；质量可变 → 路由/蒸馏可能更简单。

2. **无损 vs 有损投机**  
   - 无损稳；有损更快但要 Eval。合规场景偏无损。

3. **独立草稿模型 vs 自推测头**  
   - 独立灵活、多占资源；集成头部署简单、训练成本有。

4. **与连续批处理共存**  
   - 引擎需同时调度草稿与验证；成熟度因版本而异，升级要回归。

## FDE 现场怎么用

- **试点**：选高接受率意图（SQL 草稿、表单填充）A/B，而不是全局一开。  
- **容量**：草稿模型显存与调度写进容量表。  
- **观测**：接受率、平均每步接受长度、净加速比、错误率。  
- **关闭开关**：接受率跌破阈值自动 fallback 纯大模型。  
- **客户话术**：「加速解码，不故意改答案分布」——若有损则诚实说清。

## 课堂小结

推测解码用「小稿大核」换解码吞吐，红利取决于接受率。FDE 按意图试点、可观测、可回退。下一篇转向训练侧：分布式与 FSDP。


## 深入：接受率优化

- 草稿与目标同一 tokenizer/词表对齐；  
- 对模板化输出（JSON 字段序）接受率通常更高；  
- 降低目标温度可提高一致（但改变产品随机性，需产品同意）；  
- γ（草稿长度）太大：老拒；太小：加速有限——需扫描。  

### 现场检查清单
- [ ] 按意图开关而非全局强制
- [ ] 接受率与净加速看板
- [ ] 低接受率自动 fallback
- [ ] 无损/有损模式文档化并 Eval
- [ ] 草稿模型版本进 registry

### 常见误区
引用公网「2×加速」当合同；高温度闲聊全局开启；忽略草稿卡成本后总成本反而上升。


## 易混点

- 与「推测执行 CPU」仅是类比，实现是 draft+verify token。  
- 无损指分布意义下可对齐，不指标杆分数比特级一致。  
- 加速比强烈依赖接受率，必须用自己的流量测。

## 风险登记

草稿模型若来自另一许可证或另一厂商 API，要单独过合规；加速特性不能引入影子依赖。
