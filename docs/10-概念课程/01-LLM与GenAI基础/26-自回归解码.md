# 自回归解码

一句话直觉：LLM 一次只认下一个 token——把「写文章」拆成数百次条件预测；并行能加速预填充，但开放生成的主路径仍是串行解码。

## 直觉讲解

**Autoregressive Decoding（自回归解码）** 指序列生成服从：

\[
P(x_1,\ldots,x_T)=\prod_{t=1}^{T} P(x_t\mid x_{<t})
\]

每个新 token 依赖已生成前缀（及输入条件）。这解释了：

- 为何输出长度几乎线性决定解码时间；  
- 为何早段选错会「错上加错」；  
- 为何 KV Cache 关键；  
- 为何约束解码要逐步 mask。

阶段再强调一次：

| 阶段 | 并行性 | 用户感知 |
|------|--------|----------|
| Prefill | 高（吃输入） | TTFT |
| Decode | 逐步串行 | 后续字速 |

**投机解码（speculative decoding）**：小模型起草多 token，大模型一次验证——用并行验证换吞吐，数学上仍对齐大模型分布（在标准算法下）。

```mermaid
flowchart LR
  Pref[Prefill 输入] --> T0[采样 x1]
  T0 --> T1[采样 x2 | x1]
  T1 --> T2[采样 x3 | x1:2]
  T2 --> More[...]
```

非自回归/扩散语言模型等是研究与部分产品方向，但当前主流文本 LLM API 仍是自回归族。

## 工作示例（数字/场景）

**账本**：60 token/s，要写 600 token → 约 10s 解码，不含 TTFT。若提示要求「详尽长文」，延迟预算先炸。优化：限长、提纲、结构化短字段。

**错误传播**：第 5 个 token 选错实体名，后面 500 token 都围绕错名展开。缓解：工具查实体、低温、分阶段「先槽位后散文」。

**流式输出**：不减少总计算，但降低**感知等待**；首包快 + 稳定字速体验更好。注意：下游若需完整 JSON，别边流边入库。

**停止条件**：`stop`、eos、最大长度、外部校验失败打断。停止设计不良 → 胡话续写或费用炸。

## 面试常问取舍

1. **能否完全并行生成整句？**  
   - 标准 AR 不行；有非 AR 研究，质量/兼容性另说。投机解码是「看起来并行」的实用折中。

2. **beam search 呢？**  
   - 多假设并行维持，仍随长度扩展，聊天少用。

3. **温度与 AR 关系？**  
   - 每步分布的形状；不改变 AR 结构。

4. **批处理如何加速？**  
   - 连续批处理提高硬件利用率，不消除单序列的逐步依赖。

## FDE 现场怎么用

- 一切延迟讨论用「输出 token / 速度 + TTFT」估算。  
- 产品文案与 `max_tokens` 联合设计。  
- 需要强结构时：工具调用或约束解码，而不是长散文后解析。  
- 流式 + 取消：用户点停要能中止计费生成。  
- 教育客户：更强模型若更慢，总时长可能更差——看端到端。

### 与 Agent 多轮

每轮工具返回又触发新的 prefill/decode。Agent 慢常常是**轮次 × AR**，不是单次模型不够大。控制工具轮与观察体积。

### 数值稳定性与确定性

贪心解码在多数实现接近确定，但不完全保证跨硬件位级一致。金融对账要用业务幂等，不依赖 token 级 bit-exact。

### 对比扩散

图像扩散多步迭代去噪；文本 AR 多步扩词。都「多步」，依赖图不同。多模态系统里两者可能叠用。

## 深入：取消与计费

用户点停止时，应同时：
- 取消服务端生成；
- 停止计费扩展（按厂商规则）；
- 保存已生成部分（若产品需要）。

忽略取消，是账单事故高频原因。

## 课堂小结

自回归解释了串行代价与错误传播。限长、流式、约束与工具，是应用层与范式共处的方式。

## 补充：输出长度产品化

在 UI 提供「短/中/长」并映射 `max_tokens` 与提示条款。把长度选择权交给用户，往往比后端猜更省钱且更满意。
