# Tokenization 与 Token

一句话直觉：模型不读「字」，它读的是切好的计价单位——token；切法决定成本、延迟、截断点与多语言公平性。

## 直觉讲解

**Tokenization（分词 / 子词切分）** 把原始文本映射为模型词表（vocabulary）中的离散 ID 序列。现代 LLM 多用 **BPE（Byte Pair Encoding）**、**WordPiece** 或 **Unigram** 一类子词算法：高频词往往整词一个 token，生僻词拆成多个子词甚至字节级片段。

关键事实：

| 概念 | 含义 | FDE 为何在意 |
|------|------|--------------|
| Token | 模型输入/输出的原子单位 | API 按 token 计费与限流 |
| Vocabulary | 合法 token 集合 | 词表外现象、特殊符号行为 |
| Tokenizer | 文本 ↔ token ID 双向映射 | 同一段话在不同模型上 token 数不同 |
| Special tokens | `<bos>`、`<eos>`、`[INST]` 等 | 对话模板、停止条件 |

「一个中文汉字 ≈ 1–2 token、一个英文单词 ≈ 1–1.3 token」只是经验区间，**必须以目标模型的 tokenizer 实测**。代码、JSON、空格缩进、emoji、罕见专有名词通常更「贵」。

```mermaid
flowchart LR
  A[原始文本] --> B[Tokenizer.encode]
  B --> C[token ID 序列]
  C --> D[Embedding 查表]
  D --> E[Transformer 计算]
  E --> F[logits → 采样下一 token]
  F --> G[Tokenizer.decode]
  G --> H[可读文本]
```

与「字符」「单词」的差别：分词是**数据驱动的压缩**，不是语言学上的词边界。同一语义在不同 tokenizer 上长度可差 20%–100%+，这会连锁影响上下文窗口占用、RAG 切块策略、以及「还能塞多少 few-shot」。

## 工作示例（数字/场景）

**场景 A：同一段中英混排提示**

假设业务提示约 800 汉字 + 200 英文词 + 一段 40 行 JSON schema。

| 片段 | 粗估 token（示意） | 备注 |
|------|-------------------|------|
| 800 汉字说明 | 800–1600 | 取决于是否常见词 |
| 200 英文词 | 200–280 | 技术词可能更多 |
| 40 行缩进 JSON | 常比「看起来」贵 1.5–3× | 空格、引号、键名重复 |
| 合计粗估 | 约 1.5k–3k+ | 必须用 `tiktoken` / 厂商 tokenizer 校准 |

若上下文窗口 8k，系统提示 + 工具 schema + 检索片段再占 4k，留给对话历史的预算可能只剩 1–2k——**不是「字数够」，是 token 预算不够**。

**场景 B：计费偏差**

客户按「字数」估算成本，你按 token 报价。若实际 tokenizer 对代码块膨胀 2×，月账单可能翻倍。FDE 做法：用生产流量抽样，对目标模型跑一次 token 直方图，再定 `max_tokens`、截断策略与缓存边界。

**场景 C：停止与特殊符号**

模型生成到 `<eos>` 或对话模板结束符才停。若你的后处理把特殊 token 当普通文本拼接，会出现「截断半截」「重复开场白」。调试时同时看 **decode 前的 token ID** 与 **stop sequences**。

## 面试常问取舍

1. **更细粒度（接近字节）vs 更粗粒度（接近词）**  
   - 细：覆盖任意字符串、OOV 少，但序列更长 → 算力/费用↑。  
   - 粗：序列短、吞吐高，但对罕见词与跨语言不均。

2. **统一多语言词表 vs 分语言词表**  
   - 统一便于多语对话与代码混排；但对低频语言可能「一句话很多 token」，公平性与成本都吃亏。

3. **业务侧自己再切词 vs 信任模型 tokenizer**  
   - RAG 切块、计费预估必须对齐模型 tokenizer；搜索侧可用另一套分词，但要清楚「检索单位 ≠ 模型单位」。

4. **压缩提示（缩写、去空格）是否一定省钱？**  
   - 不一定。破坏可读结构可能导致模型胡猜，重试成本更高；应测 token 与任务指标，而不是只看字符数。

## FDE 现场怎么用

- **立项周**：锁定主模型与备用模型，分别导出 tokenizer，建立「典型请求」token 基线（P50/P95）。  
- **设计接口**：所有长度限制写成 `max_input_tokens` / `max_output_tokens`，UI 文案避免写「最多 N 字」。  
- **排障**：超长截断、计费异常、中英混排变慢——先打印 token 数与 top 膨胀片段（JSON、base64、日志原文）。  
- **与客户对齐**：报价单附「按目标模型 tokenizer 计量」条款；给出样例文本的实测 token。  
- **工程清单**：对话模板版本与 tokenizer 版本一起进变更记录；换模型先做 token 回归。

## 深入：计费、截断与多语言公平

### 为什么「中文更贵」经常成立
子词词表由训练语料统计决定。若语料英文偏多，中文同一信息量常需更多 token。这不是道德问题，而是压缩率问题。企业若以中文为主，评估模型时要把**同等业务语义下的 token 倍率**写进成本模型，而不是只看官方 $/1M tokens。

### 特殊空格与不可见字符
从 PDF/网页粘贴的文本常含不间断空格、零宽字符、全角标点。它们可能：
- 变成意外 token，破坏关键词精确匹配；
- 让「看起来一样」的前缀无法命中 Prompt 缓存；
- 在工具参数里导致校验失败。

现场建议：入库前做 Unicode 规范化（如 NFKC）与空白折叠策略，并在评测集里放脏样本。

### 与 RAG 切块的对齐方式
切块长度若按字符估，容易在模型侧超窗。正确做法：
1. 用目标 tokenizer 计量切块；
2. 块之间留重叠（按 token 计）；
3. 元数据（标题、面包屑）单独占预算，不要挤掉正文关键句。

### 常见误区再澄清
「加空格就能省 token」在 BPE 上往往不成立；「换成英文提示一定更短」也要实测。唯一可信的是：**对目标模型 encode 后再谈优化**。

## 课堂小结

Token 是计费、限流与窗口的共同货币。FDE 不背诵词表算法细节，但必须能：实测、做预算、解释中英与代码膨胀，并把 tokenizer 版本纳入变更管理。下一篇将把「token 预算」升级为完整的上下文窗口治理。
