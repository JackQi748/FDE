# 约束解码（Constrained Decoding）

一句话直觉：与其生成完再祈禱 JSON 合法，不如在每个 token 上把非法续写的概率抹掉——让模型「只能走合法语法的路」。

## 直觉讲解

**Constrained Decoding（约束解码）** 指在解码过程中，根据语法、正则、有限状态机（FSM）、上下文无关文法（CFG）或 JSON Schema 等，动态屏蔽不合法的下一 token，使采样只在合法集合中发生。

对照三条路：

| 方法 | 何时约束 | 优点 | 代价 |
|------|----------|------|------|
| 提示「请输出 JSON」 | 生成前 | 零基建 | 仍会破格式 |
| 生成后校验 + 重试 | 生成后 | 实现简单 | 延迟/费用×重试 |
| **约束解码 / 语法引导** | 每步 | 合法率极高 | 集成与性能开销 |

相关能力商标签：JSON mode、grammar、regex，或推理侧库（如 Outlines、Guidance、XGrammar 等思路）。本质都是 **mask logits**。

```mermaid
stateDiagram-v2
  [*] --> S0: 开始
  S0 --> S_obj: 读到 {
  S_obj --> S_key: 键名中
  S_key --> S_colon: 键结束
  S_colon --> S_val: :
  S_val --> S_obj: 值结束且还需字段
  S_val --> S_end: 值结束且可闭合
  S_end --> [*]: }
```

约束越强，自由度越小：对开放闲聊可能「写死」；对 API 填参、表单、DSL 则刚刚好。

## 工作示例（数字/场景）

**场景：工单系统写回**  
字段：`priority ∈ {P0,P1,P2}`，`assignee` 为邮箱正则。  
- 纯提示：1000 次调用中格式失败 3%–8%（示意），需重试。  
- Schema 约束：格式失败接近 0，剩下来的是**语义错**（优先级标错）——那是另一类问题，该用业务规则与审核，而不是再加热。

**延迟账**：后验重试平均 1.2 次额外调用，P95 延迟可能从 2s 变成 5s+；约束解码可能略增每步开销，但去掉重试尾部，P95 反而更好——要以压测为准。

**场景：SQL 方言**  
CFG 保证语法可解析，不保证「不会删表」。约束≠安全；写操作仍要权限、白名单与人工闸。

## 面试常问取舍

1. **JSON mode 是否等于 Schema 约束？**  
   - 不一定。有的仅保证「是 JSON」，不保证字段与类型；要读厂商文档。

2. **约束是否降低正确率？**  
   - 格式正确率↑；若 Schema 与自然语言冲突（逼模型选非法业务值），可能「瞎填合法值」。Schema 设计要留可选/枚举合理。

3. **正则约束 vs 完整 Schema**  
   - 正则轻；嵌套对象、可选字段用 Schema/文法更合适。

4. **与工具调用（function calling）关系**  
   - 工具调用常是另一条结构化通道；可与约束互补。别在自然文本频道里手搓巨型 JSON，能走 tool 就走 tool。

## FDE 现场怎么用

- 所有「写库/调 API」输出默认：Schema + 校验 +（可选）约束解码。  
- 错误分层：`parse_error` / `schema_error` / `business_error` 分指标看板。  
- PoC 对比三列：仅提示、提示+重试、约束解码——用合法率、延迟、成本说话。  
- 枚举值与后端常量同源生成 Schema，避免前后端枚举漂移。  
- 安全：约束只解决形状，不解决授权。

### 实现注意点

- **词表分词干扰**：文法在字符层合法，在 token 层可能卡在半个多字节字符——成熟库会处理 token 对齐。自研 mask 要测中文与转义。  
- **流式输出**：约束与 streaming 可共存，但客户端要按「最终合法对象」消费，不要半截 JSON 入库。  
- **日志**：保留 raw 文本与 schema 版本，便于复盘「合法但错义」。

### 何时不要用硬约束

开放写作、复杂自然语言说理、需要罕见格式的文学性输出——硬文法会显得僵。可采用「主字段约束 + 长文本字段自由」的混合 Schema。

## 深入：与校验修复的分工

理想分层：
1. 约束解码尽量一次合法；
2. 本地确定性修复处理围栏/逗号；
3. 模型修复限 1 次；
4. 仍失败则降级人工或规则。

不要把「无限重试直到 JSON 好」当成稳健性——那是成本无界。

### 枚举漂移事故
后端改了优先级枚举，Schema 未同步，约束解码会逼模型从旧枚举里选——合法但错。Schema 必须进 CI。

## 课堂小结

约束解码把语法正确率推到极高，但语义与授权仍靠系统其他层。形状与真值，分开治理。

## 补充：文法过大时的性能

超大 JSON Schema 转文法可能导致编译慢或运行时 mask 开销高。优化：
- 拆分多步 schema；
- 枚举别过大（成千上万 SKU 不要进枚举，改校验+检索）；
- 长自由文本字段不要约束到字符级正则。

### 决策树
需要写库？→ 要 Schema。  
字段少且稳？→ 约束解码优先。  
字段极动态？→ 工具调用 + 服务端校验。  
仅展示给人类？→ 可放宽，但仍建议轻度结构。
