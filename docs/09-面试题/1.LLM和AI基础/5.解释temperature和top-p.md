## 05 解释 temperature（温度）与 top-p。在企业工作流中，什么时候会将 temperature 设置为0？


> **TL;DR（一句话总结）**
> 温度会对下一个token的概率分布做缩放（0代表贪心argmax，数值越高，分布越平缓）；top-p保留概率累加超过p的最小token集合。在信息抽取、结构化输出、工具调用与评估任务中使用temperature=0；但要明确一点：它只是降低结果方差，并不能消除幻觉。

### 作答思路
清晰定义两个参数，说明实际工程里的默认值，再回答核心问题：哪些企业工作流需要输出确定性，哪些需要多样性。主动指出常见误区（temperature=0不等于“不会产生幻觉”）。

### 高分回答
模型在每一步都会输出下一个token的概率分布。**温度**会在采样前对这个分布做缩放：低温会让分布变尖锐，偏向概率最高的token；高温会拉平分布，给低概率token更多被选中的机会。当temperature=0时，每次都会取argmax，也就是贪心解码。
temperature=0并不是“真值开关”：它只是重复给出同一个猜测，不代表猜测一定正确。

而**top-p（核采样）**则是截断概率分布，只保留累计概率超过p（例如0.9）的最小token集合，然后在这个集合内采样；它会根据模型自身置信度，动态调整候选token数量。两个参数会互相影响，因此标准做法是调其中一个，另一个保持默认值。

> Logits（对数几率） → Temperature scale（温度缩放）
> 分支1：temp = 0 → Argmax / greedy（取最大概率/贪心解码） → Next token（下一个token）
> 分支2：temp > 0 → Top-p / top-k prune（top-p/top-k裁剪） → Sample from survivors（从剩余候选里采样） → Next token（下一个token）

用数字直观理解这两个参数。假设temperature=1时，模型对4个候选token的下一词概率分布为：0.60、0.25、0.10、0.05。经过温度缩放后，概率会变为下表：

| Temperature（温度） | Token A | Token B | Token C | Token D | Effect（效果） |
| ---- | ---- | ---- | ---- | ---- | ---- |
| 0.5 | 0.83 | 0.14 | 0.02 | 0.01 | 分布变尖锐：首选token占绝对主导 |
| 1.0 | 0.60 | 0.25 | 0.10 | 0.05 | 模型原始分布 |
| 2.0 | 0.43 | 0.28 | 0.17 | 0.12 | 分布被拉平：低概率token有了实际机会 |
| 0 | 1.00 | 0 | 0 | 0 | 贪心解码：永远选择Token A |

沿用上面这个分布：top-p=0.9会保留Token A、B、C（累计概率0.60→0.85→0.95，在第三个token处累计概率超过0.9），永远不会采样D。
这里可以看到top-p相比固定top-k的优势：当模型很自信，单个token概率就达到0.95时，top-p只保留这一个token；而如果分布分散在40个合理候选token上，它就保留全部40个。候选集合会自适应模型自身的置信度，这也是top-p相比top-k，现在更适合作为默认采样参数的原因。

#### 在企业工作流中，我会把temperature设为0（或接近0）的场景：
- **信息抽取与分类**：从发票提取字段、工单路由、条款标记。这类场景要求相同输入得到相同输出。
- **结构化输出**：给下游系统输出JSON，采样带来的随机性会破坏格式规范。
- **工具/函数调用**：生成调用参数，要求稳定、可复现。
- **评估与调试**：可复现性让我们能够准确衡量模型退化；在高温度下跑评估，引入的噪声会被误判为模型质量变化。

适合temperature > 0的场景：营销文案变体生成、头脑风暴、合成数据生成（需要多样性），以及对话场景——轻微的输出变化会让对话更自然。
参考取值：确定性任务0~0.3；通用对话约0.7；创意生成1.0及以上。

两个体现专业度的注意点：
第一，temperature=0只能降低方差，不能降低错误率。如果模型本身笃定给出错误答案，无论温度高低结果都是错的，因为幻觉是事实对齐问题，不是采样问题。
第二，实际生产中temperature=0也无法做到绝对确定性：批量推理服务、浮点数计算的非确定性，偶尔依然会导致token变化。因此不要向客户承诺逐比特完全一致的输出；承诺“低方差+评估验证的质量”更合适。

### 面试官接下来可能追问的问题
- “客户设置temperature=0，但仍然遇到幻觉，你怎么解释？”
  采样参数控制的是输出方差；事实正确性靠检索增强生成（RAG）、引用溯源、更好的提示词、校验机制来控制。
- “什么场景下，temperature=0反而有害？”
  需要多样性的任务；另外贪心解码在长文本自由生成时，容易产生重复、退化的文本。
- “如何选择温度参数？”
  靠实验：搭建小型评估集做参数扫描；不要盲目套用0.7这个经验值。

### 常见错误
- 浅显解释原理（只说“温度代表创造力”），没有分布层面的解释。这种说法对客户够用，但AI实验室面试中会显得理解太浅。
- 声称temperature=0可以保证确定性，或者保证事实准确。这两点都是错的，面试官会专门留意这个坑。
- 同时调temperature和top-p，却不说明二者会互相影响。
- 不结合评估：凭感觉选择采样参数，而不是靠指标衡量。这是FDE（Foundation Data Engineering，基础数据工程）面试重点排查的思维误区。

### 核心要点
- temperature=0是贪心argmax；它降低方差，但不降低错误，无法解决幻觉。
- temperature和top-p选一个调参，另一个保持默认，因为两者存在相互作用。
- 贪心解码适合抽取、JSON结构化输出、工具调用、评估任务；需要多样性的任务要用temperature>0。

**编者注**

能体现出高级工程师水平的做法，就是抢在面试官提问之前主动提出**服务侧的非确定性问题**：温度设置为0代表贪心解码，**并不代表输出结果比特级完全一致**，一旦引入批处理和浮点数运算，结果就会出现差异。向客户承诺输出可复现，结果线上生产环境却出现个别token发生变化，这是真实发生过的线上重大问题。因此对外要表述为做到输出低方差、经过评估验证保证质量，**绝对不要给出100%可复现的保证**。

贪心解码会掩盖一类故障现象：当生成长篇自由文本输出时，温度等于0可能造成模型陷入循环、输出退化，无限制重复同一段语句。原因是取最大值（argmax）没有机制可以从高概率的局部死循环中跳出来。

做信息抽取、JSON结构化输出的时候，该问题不会显现。但有些团队为了“稳妥”，全局把温度置为0，结果长篇文本生成效果变差，却始终没有把问题根源和采样策略的改动关联起来。
