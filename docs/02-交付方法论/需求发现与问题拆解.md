# 需求发现与问题拆解

FDE 的日常入口往往是一句危险的话：「我们要做个 AI + ___」。本篇教你把这句话拆成**可验证的问题**，并与面试中的 [Decomposition](../04-面试通关/Decomposition拆解面.md) 同构——现场会做，面试才会像。

---

## 1. 原则

1. **先用户与结果，后功能与模型**
2. **子问题是问题的部件，不是「建项目的阶段」**
3. **大声说出假设，邀请推翻**
4. **找到硬点**（做错了会让结果崩掉的那一块）
5. **先给一个可证伪的下一步**，再谈大架构

---

## 2. 发现访谈：问什么

完整提纲见 [发现访谈提纲](../08-工具箱与清单/发现访谈提纲.md)。核心六问：

| # | 问法 | 你在挖什么 |
|---|------|------------|
| 1 | 今天谁在做这件事？一步步怎么做？ | 真实工作流 |
| 2 | 怎样算做好了？谁用什么数字看你？ | 指标与考核 |
| 3 | 最近一次失败是什么？代价？ | 风险与边缘 |
| 4 | 数据在哪？谁能碰？能否出网？ | 约束 |
| 5 | 为什么是现在？为什么找我们？ | 动机与政治 |
| 6 | 如果只能改善 20%，你选哪？ | 优先级 |

**追问句式**：「能否带我看一次真实案例？」「如果系统给错答案，谁会怎样？」

---

## 3. 问题陈述模板

写满再谈方案：

```text
【用户】在【场景】下，需要【结果】，
今天通过【现状】完成，主要问题是【痛点】，
成功时【指标】从 A 到 B，
约束包括【数据/安全/时间/组织】，
本次非目标是【】。
```

示例：

```text
【一线法务】在【供应商合同初审】下，需要【标出与模板不符的高风险条款】，
今天通过【人工通读】完成，主要问题是【积压与漏标】，
成功时【初审人均时长】从 45min 到 20min 且【高风险漏检】不高于基线，
约束包括【合同不出域、需审计】，
本次非目标是【自动改写合同、商务谈判建议】。
```

## 4. 拆解方法（现场版 Decomposition）

对问题陈述，拆 **3–5 个子问题**（问题部件）：

错误拆法（阶段）：「先采数据 → 再训练 → 再上线」  
正确拆法（部件）：「条款差异定义不清」「模板版本混乱」「高风险类目无标注」「审出结果如何写回系统」

然后标出 **硬点**：例如「高风险类目无标注」→ 没有标签就无法 eval → 试点必挂。

最后给 **具体下一步**：「本周与 2 名律师标 30 份合同的高风险句，形成 v0 量规与黄金集。」

---

## 5. 干系人与冲突

| 角色 | 典型诉求 | 你的策略 |
|------|----------|----------|
| 业务 sponsor | 尽快见效、可对外讲故事 | 时间盒试点 + 可展示指标 |
| 一线用户 | 少添乱、嵌入现有工具 | 观测一天；做助手而非新系统 |
| IT | 稳定、标准、少开口子 | 早亮数据流与权限图 |
| 安全/法务 | 风险为零的幻觉 | 分级数据、HITL、审计、书面边界 |
| 采购 | 合同与报价 | 分离 POC 与生产条款 |

当诉求冲突时，写 **决策备忘录**：选项、利弊、推荐、需要谁拍板——见 [客户沟通](./客户沟通与阻力处理.md)。

---

## 6. ROI 与成功指标

避免虚荣指标（「回答了多少问题」）。优先：

| 类型 | 例子 |
|------|------|
| 效率 | 人均处理时长、等待时间 |
| 质量 | 差错率、返工率、与专家一致率 |
| 风险 | 漏检、合规事件 |
| 采用 | 周活、建议采纳率 |
| 成本 | 单次推理成本、人工分钟成本 |

ROI 叙述结构：**基线 → 试点增量 → 年化假设 → 主要风险假设**。写明假设，防止被当成承诺。

## 7. 示例对话（节选）

> 客户：我们要做企业知识库机器人。  
> FDE：谁会每天用？他们现在问谁？答错的代价是什么？  
> 客户：新员工问老员工，主要浪费时间，答错一般能发现。  
> FDE：那硬点可能是「知识过期」和「找不到人」而不是「不会聊天」。我们能否先选一个部门、一类问题（如报销），两周测「助手建议被采纳率」？  
> 客户：可以。  
> FDE：好，那非目标是全公司开放域自动回答。我会把问题陈述发你确认。

## 8. 构建前三问与「一天能解就一天解」

> 精读补充自 [Palantir FDE 起源演讲](https://www.youtube.com/watch?v=1OMHGsUZiqA)（四则现场故事的可迁移部分）。与上文访谈六问互补，偏「动手前校准」。

在画大 BI / 大 Agent 之前，先对齐：

1. **想完成什么？**（核心目标）  
2. **有了解决方案之后会发生什么？**（下游动作与责任）  
3. **客户今天怎么解决？**（现状路径）

客户常描述的是**解决方案**（「我要 14 指标仪表盘」），FDE 要挖到**问题**（「周一先看哪辆车迟到」）。公开故事里，47 页需求最终收敛成一个调度 Slack 提醒——数小时交付。

**若问题能在一天内闭环：直接构建、交付、收口。** 不要为了「产品战略叙事」强行做大。小块解决 → 赢信任 → 才拿到真问题的访问权。

---

## 9. 行动胜于言语：现场观察信号

最有价值的情报很少在问卷里。**驻场者获得真相。** 观察重复动作、跨工具复制粘贴、烦躁的「我不得不这样」——都是机会信号。开场可问：「你早上最烦人的部分是什么？」

公开故事：数据同事抵制 Parquet，只因习惯双击 CSV；现场看清后做了查看器，迁移当周通过，管道从约 17 小时降到约 2 小时。启示：反对声背后可能是工具缺口，不是「用户顽固」。

### 语言 / 本体（名词与动词）

同一实体被叫 customers / clients / billing entities / org IDs 时，集成必炸。FDE 要摸清：哪些词被过度加载、系统边界与不可替换的 SoR、人们描述问题时的用语。**定义术语，往往就定义了后续叙事**（与数据「语义层」同构，见 [限域分析助手](../06-行业案例/06-限域数据分析助手.md)）。

## 10. Checklist

- [ ] 问题陈述已书面确认
- [ ] 3–5 个子问题与硬点已标出
- [ ] 指标与基线存在（或本周可测基线）
- [ ] 非目标清晰
- [ ] 下一步是具体可证伪动作
- [ ] 已用 §8 三问校准；能一天解的没被做成季度项目
- [ ] 至少做过一次真实旁观（或等价屏幕共享工作流）
